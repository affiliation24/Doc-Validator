# Doc Validator

Сервис автоматической проверки финансовых документов на соответствие регламентам компании.

Загружаешь счёт, договор, акт или платёжное поручение — система извлекает данные, сверяет с регламентами и выносит вердикт с объяснением.

## Как это работает

```
PDF / скан / текст
      ↓
OCR (pdfplumber / tesseract) — извлекает текст из файла
      ↓
LLM Extract — структурирует данные в JSON     [gpt-oss-20b, JSON mode]
      ↓
Hard Checks — принудительные проверки по сумме, категории, валюте
      ↓
RAG Retrieve — семантический поиск регламентов [ChromaDB + multilingual embeddings]
      ↓
LLM Validate — сверяет данные с регламентами  [gpt-oss-120b, JSON mode]
      ↓
Enforce — блокирующие hard checks перекрывают вердикт модели
      ↓
Результат: APPROVED / REJECTED
+ список нарушений с приоритетом
+ uncertain_fields (что модель не смогла проверить)
+ human_comment (вывод на русском для сотрудника)
```

**Стек:** Python · FastAPI · Groq API · ChromaDB · Sentence Transformers · pdfplumber · Tesseract OCR

## Возможности

- Приём документов в виде текста, PDF или изображения (JPG, PNG)
- Извлечение 30 полей через LLM с постобработкой типов, включая полный набор
  реквизитов бланка 0401060: стороны платежа, банки, очерёдность, УИН, КБК, ОКТМО
- Принудительные проверки по числовым порогам и категориям до вызова LLM
- Семантический поиск релевантных регламентов через мульти-запросную стратегию
- Валидация с уровнями серьёзности: `ошибка` / `предупреждение`
- Приоритеты нарушений: `БЛОКИРУЮЩИЙ` / `ТРЕБУЕТ_ВНИМАНИЯ` / `ИНФОРМАЦИОННЫЙ`
- Обработка неопределённости: `uncertain_fields` с объяснением сомнений
- Веб-интерфейс в стиле министерства с историей и статистикой
- REST API с автодокументацией (Swagger UI)
- Журнал обработанных документов с эндпоинтами `/history` и `/stats`
- Управление регламентами через `rules.txt` без изменения кода
- Покрытие тестами: extractor, retrieval, pipeline (pytest)

## Быстрый старт

### 1. Клонируй репозиторий

```bash
git clone https://github.com/твой-username/doc-validator.git
cd doc-validator
```

### 2. Установи зависимости

```bash
python -m venv .venv
source .venv/bin/activate  # Windows: .venv\Scripts\activate
pip install -r requirements.txt
```

Для OCR сканов дополнительно установи Tesseract:

```bash
# macOS
brew install tesseract tesseract-lang

# Ubuntu/Debian
sudo apt install tesseract-ocr tesseract-ocr-rus
```

### 3. Создай .env файл

```bash
echo "GROQ_API_KEY=your_key_here" > .env
```

Опционально в том же файле можно переопределить модели и пути — код читает эти
переменные, значения по умолчанию указаны в скобках:

```
RULES_TOP_K=8
EXTRACT_MODEL=openai/gpt-oss-20b
EXTRACT_FALLBACK_MODEL=openai/gpt-oss-120b
VALIDATE_MODEL=openai/gpt-oss-120b
GROQ_MAX_RETRIES=3
EMBEDDING_MODEL=paraphrase-multilingual-MiniLM-L12-v2
RULES_FILE=rules.txt
RULES_DB_PATH=./rules_db
```

Получить бесплатный ключ: [console.groq.com](https://console.groq.com)

### 4. Запусти сервис

```bash
uvicorn main:app --reload --port 8000
```

При первом запуске регламенты из `rules.txt` автоматически загрузятся в ChromaDB.

### 5. Открой интерфейс

Веб UI: открой `doc_validator_ui.html` в браузере

Swagger UI: [http://localhost:8000/docs](http://localhost:8000/docs)

## Управление регламентами

Правила хранятся в `rules.txt` — по одному на строку. Строки начинающиеся с `#` — комментарии.

```
# СЧЕТА И СЧЕТА-ФАКТУРЫ
Закупка любого ПО и лицензий требует согласования IT-отдела.
Счета свыше 50 000 руб. требуют визы финансового директора.

# ГОСУДАРСТВЕННЫЕ КОНТРАКТЫ И ДОГОВОРЫ
Договоры свыше 1 000 000 руб. требуют согласования юридического отдела.
```

Заголовок секции — не просто оформление: по нему правило привязывается к типу
документа. Соответствие задано в `SECTION_DOC_TYPES` в `validator.py`:

| Секция | Тип документа |
|---|---|
| СЧЕТА И СЧЕТА-ФАКТУРЫ | `invoice` |
| ГОСУДАРСТВЕННЫЕ КОНТРАКТЫ И ДОГОВОРЫ | `contract` |
| ПЛАТЁЖНЫЕ ПОРУЧЕНИЯ, БЮДЖЕТНЫЕ ПЛАТЕЖИ | `payment_order` |
| АКТЫ ВЫПОЛНЕННЫХ РАБОТ | `act` |
| СЛУЖЕБНЫЕ ЗАПИСКИ И СОГЛАСОВАНИЯ | `approval` |
| любая другая секция | применяется ко всем документам |

При изменении файла и перезапуске сервиса база обновляется автоматически. Пересоздавать вручную не нужно.


## Запуск тестов

Тесты `test_pipeline.py` бьют по живому сервису, поэтому его нужно поднять
заранее — иначе они пропускаются:

```bash
uvicorn main:app --port 8000 &
pytest test/ -v
```

```
test/test_extractor.py::test_extract_invoice_basic              PASSED
test/test_extractor.py::test_extract_contract                   PASSED
test/test_extractor.py::test_extract_foreign_currency           PASSED
test/test_pipeline.py::test_pipeline_status[software_over_limit] PASSED
test/test_pipeline.py::test_pipeline_status[small_act_approved]  FAILED
test/test_retrieval.py::test_retrieval_software_purchase        PASSED
...
====== 15 passed, 1 failed ======
```

Падение `small_act_approved` известное и содержательное: тест ждёт `APPROVED`
для акта на 3 000 руб., но регламенты требуют от акта подписи сторон и период
выполнения работ, а в тексте-заглушке их нет — валидатор честно отклоняет
документ. Либо промпт должен считать отсутствие поля в неструктурированном
тексте неопределённостью, а не нарушением, либо тест-кейс нужно заменить на
документ с полным набором реквизитов.

## Архитектурные решения

**Две модели с разными ролями** — лёгкая `openai/gpt-oss-20b` для извлечения данных (скорость), тяжёлая `openai/gpt-oss-120b` для валидации (точность). Разделение ответственности снижает стоимость и повышает качество. Обе вызываются в JSON-режиме (`response_format={"type": "json_object"}`), поэтому ответ не может прийти в виде markdown или текста вокруг JSON.

**Hard checks решают вердикт, а не подсказывают его** — числовые пороги и реквизиты проверяются детерминированно в коде. LLM формулирует и объясняет, но если hard check нашёл блокирующее нарушение, `enforce_blocking_checks` принудительно ставит `approved = false` и дописывает пропущенное нарушение. Модель не может одобрить документ вопреки коду.

**Пороги — одна константа на правило** — `CFO_LIMIT`, `HEAD_LIMIT`, `TENDER_LIMIT`, `LEGAL_CONTRACT_LIMIT` в `validator.py`. Из них собирается и системный промпт, и код проверок, поэтому промпт и логика не могут разойтись.

**Мульти-запросный RAG по фактам документа** — запросы строятся под конкретный документ: по категории и типу, по обязательным реквизитам, а запросы про лимит, валюту и банковские реквизиты добавляются только если документ действительно превышает порог, оформлен в валюте или содержит счёт. Результаты объединяются по минимальному расстоянию и отсекаются порогом `MAX_DISTANCE`.

**Секции rules.txt — это фильтр, а не оформление** — заголовок секции задаёт
тип документа, к которому относятся её правила, и попадает в метаданные
ChromaDB. Поиск по платёжному поручению не забивается правилами про счета и
акты. Секция, не описанная в `SECTION_DOC_TYPES`, считается общей, поэтому
новый заголовок в файле не ломает поиск. Если тип документа не распознан,
фильтр снимается — лучше лишние правила в промпте, чем пропущенное нарушение.

**Мультиязычные эмбеддинги** — `paraphrase-multilingual-MiniLM-L12-v2`. Англоязычная `all-MiniLM-L6-v2` на русских регламентах давала практически случайную выдачу. Эмбеддинги нормируются, поэтому квадрат L2 в Chroma равен косинусному расстоянию и порог релевантности имеет смысл. Имя модели входит в хэш индекса — при её смене база пересобирается автоматически.

**rules.txt вместо hardcode** — регламенты живут в текстовом файле. База ChromaDB пересоздаётся только при изменении файла (хэш-сравнение). Добавить правило = одна строка в файле.

**Фолбэк модели при извлечении** — схема извлечения насчитывает 30 полей, и на
плотных документах вроде платёжного поручения лёгкая модель иногда не добирает
её до конца: Groq отклоняет такой ответ в JSON-режиме. Вместо ошибки запрос
переигрывается на `EXTRACT_FALLBACK_MODEL`. Лишний вызов происходит редко, а
пайплайн не падает на самых сложных документах.

**Ретраи на 429** — free tier Groq даёт 8000 токенов в минуту, промпты здесь
длинные. `llm.with_rate_limit_retry` ждёт ровно столько, сколько называет сам
Groq в тексте ошибки, и повторяет вызов — вместо 500 в ответ пользователю.

**doc_type — код, а не текст** — модель периодически переводила enum на русский
(`"акт"` вместо `"act"`), из-за чего проверки, завязанные на тип документа,
молча переставали срабатывать. Значение нормализуется в коде, а не только
инструкцией в промпте.

**`temperature=0`** — детерминированные ответы. Один и тот же документ всегда даёт одинаковый результат. Важно для аудита и воспроизводимости.

**uncertain_fields** — если модель не уверена в поле, она не пропускает документ, а явно указывает что именно вызывает сомнение и какие данные нужны для проверки.
